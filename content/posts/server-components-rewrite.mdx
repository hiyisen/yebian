这个博客的前一版是典型的客户端渲染架构：浏览器下载一个 JS bundle，再由它去请求 Markdown 文件、解析、高亮、渲染。听起来没什么问题，直到我把网络限速调到 3G 才发现——首屏白屏了整整四秒。

真正让我下决心重写的，不是这四秒，而是另一个更本质的疑问：**这些工作里，有多少是必须在用户设备上做的？** 文章内容不会因为访问者不同而变化，那么解析和高亮本该只做一次。

## 先搞清楚 RSC 到底解决什么

React Server Components 的核心不是「服务端渲染」，而是*组件可以被拆成两个部分*：一部分只在服务端执行一次，另一部分才进入客户端 bundle。这带来一个直接后果——你可以放心地在组件里写 `fs.readFileSync`，而它永远不会出现在浏览器里。

<Callout type="note" title="判断标准只有一个">
它是否依赖浏览器 API 或用户交互？如果都不是，那它大概率不该进 bundle。
</Callout>

判断一个组件该不该是 Server Component，问题其实只有这一个。

## 迁移的三个步骤

### 把数据获取下沉到组件内部

以前是页面上层统一取好数据，一层层往下传。现在每个组件自己取自己需要的东西。少写了很多类型定义，也再没有「为了传一个字段改了五层 props」这种事。

```tsx
// app/posts/[slug]/page.tsx —— 组件自己取数据
export default async function PostPage({ params }) {
  const post = await getPost(params.slug);
  if (!post) notFound();

  const html = await renderMarkdown(post.content);

  return <PostBody html={html} meta={post.meta} />;
}
```

### 把高亮移到构建期

原先用的是运行时高亮库，它把整个语法定义表打包进了客户端。换成构建期高亮之后，输出的就是一段静态 HTML——客户端体积直接少了 **180KB**。

<Callout type="warn" title="一个容易踩的坑">
高亮库默认会加载全部语言包。如果你只用三五种语言，记得显式声明要用哪些，否则构建时间会从 4 秒涨到 40 秒。
</Callout>

### 用静态索引替代服务端搜索

站内搜索原本要打一个接口。但其实文章总量是固定的，索引完全可以在构建期生成好，浏览器端直接匹配。省掉一个服务，响应还更快。

## 前后对比

三个指标的变化比我预期的更明显，尤其是发送给浏览器的 JS 体积。

| 指标 | 重构前 | 重构后 | 变化 |
| --- | --- | --- | --- |
| 首屏 JS 体积 | 412 KB | **96 KB** | −77% |
| LCP（3G 限速） | 4.1 s | **1.2 s** | −71% |
| 构建耗时 | 11 s | 19 s | +73% |
| 源码行数 | 3,180 | **1,240** | −61% |

构建耗时增加是唯一的代价，而它只影响我自己。这笔交易非常划算——用户的体验变好了，我的维护成本变低了，唯一变差的是一个我根本不在意的时间。

## 三个我一开始想错的地方

1. **以为 Server Component 不能有状态。** 对，但你可以把它拆开——外层的 Server Component 负责取数据，内层的 Client Component 负责交互，两者之间传的是已经序列化好的普通对象。
2. **以为所有组件都该默认 Server。** 实际上真正需要客户端执行的组件少得可怜，但把它们识别出来需要一点刻意练习。
3. **以为迁移必须一次做完。** 我是按页面逐个迁的，每迁一个就发一次版，中间没有任何一个时刻是全坏的。

---

最后说一句可能不太受欢迎的话：RSC 并没有让写代码变简单，它只是**把复杂度挪到了更合适的位置**。你依然要想清楚哪些状态属于服务端、哪些属于客户端——区别在于，现在想不清楚的代价从「用户多等三秒」变成了「构建慢一点」。

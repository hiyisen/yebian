我曾经三次打开某个框架的仓库，三次都在 `src/index.ts` 那里停下来。不是因为难，是因为从入口往下读，你面对的是一棵无限展开的树：每个函数都调用另外五个函数，读到第三百行已经忘了第一行在干嘛。

后来我改了个做法，成功率立刻上去了。

## 从问题出发，不从入口出发

不要问「这个库是怎么实现的」，要问「这个库是怎么做到 X 的」。

前者没有边界，后者有。比如你想知道「它是怎么把 Markdown 里的代码块变高亮的」，那就直接在仓库里搜关键词，找到那个函数，然后只沿着这一条链路往上看。其余的分支一律不管。

<Callout type="note" title="一个具体的操作">
在 GitHub 上按 <code>t</code> 可以进入文件搜索，直接搜功能对应的英文单词，比逐个目录翻要快一个数量级。
</Callout>

## 先把「输入输出」跑通再读实现

读代码之前，先把它跑起来，故意喂几个奇怪的输入，看它输出什么。这一步能帮你建立直觉：哪些是它真正在做的，哪些只是边界处理。

有了这个直觉再去读实现，代码就不再是一堆符号，而是「它刚才确实这么干了」的验证。

## 遇到看不懂的地方，先记下来别停

读源码最容易死在「某个工具函数看不懂」上。我的做法是：标记一下，继续往下，等到整条链路读完了再回头。

原因是——大部分看不懂的工具函数，放在完整链路里其实不需要理解细节。它们的名字已经说明了干什么，细节不影响你理解主干。

## 读完要能用自己的话讲一遍

这是检验有没有真读懂的唯二标准（另一个是能不能改它）。如果讲不出来，说明你只是「看过了」，不是「读懂了」。

---

顺带说一句：读源码的收益是不均匀的。有些库读一遍受益终生（比如状态机、解析器），有些库读完只会觉得「哦，就这样」。挑那些你真的好奇的读，别为了「我应该多读源码」而读。

暗色模式做起来不难，难的是**半年后你还敢改配色**。我见过三种做法，复杂度递增，可维护性也递增。

## 做法一：每个组件各写一遍

```css
.card {
  background: #fff;
  color: #111;
}
[data-theme="dark"] .card {
  background: #1a1a1a;
  color: #eee;
}
```

最直觉，也最容易写。前二十个组件都没问题。

问题出在第二十一个：你想把深色底从 `#1a1a1a` 改成 `#181818`，于是全局搜索替换。然后发现有三个地方用的是 `#1b1b1b`，还有两个地方是 `rgb(26,26,26)`。

<Callout type="warn" title="这种架构真正的代价">
不是写得累，是「同一个颜色散落在几十个地方」这件事本身，让任何一次配色调整都变成了考古。
</Callout>

## 做法二：只用变量，不分语义

```css
:root {
  --white: #fff;
  --gray-100: #f4f4f4;
  --gray-900: #111;
}
[data-theme="dark"] {
  --white: #1a1a1a;
  --gray-100: #222;
  --gray-900: #eee;
}
```

比第一种好得多，改色只需要动一处。但它有个隐蔽的坑：**变量名描述的是颜色，不是用途**。

于是你会写出 `background: var(--white)` 这种在深色模式下语义完全反过来的代码。半年后看这段 CSS，你没法判断这个 `--white` 到底是不是真的想表达白色。

## 做法三：语义令牌 + 单一覆盖点

```css
:root {
  --bg: #fbfaf8;
  --surface: #ffffff;
  --text: #16140f;
  --accent: #c2410c;
}

[data-theme="dark"] {
  --bg: #100f0d;
  --surface: #191815;
  --text: #f6f3ed;
  --accent: #ff7a45;
}

.card {
  background: var(--surface);
  color: var(--text);
}
```

组件里只有语义，颜色只存在于令牌层。**换主题 = 换一组令牌，组件代码一个字都不用动。**

## 我为什么选了最「笨」的

第三种写法要先把令牌表设计出来，前期多花一两个小时。对只有三五个页面的小项目来说，这看起来是过度设计。

但它的收益在第一个月就会出现：

- 想调强调色？改一行。
- 想加第三套主题（比如护眼模式）？加一段覆盖，组件零改动。
- 想知道某个颜色用在哪？反向搜令牌名就行。

而且有个附加好处：**令牌表本身就是设计规范**。设计师问「你的灰阶有几级」，你把文件发过去就行了。

<Callout type="note" title="一条经验">
如果一个颜色值在项目里出现了两次以上，它就该是一个令牌。不是因为它多复杂，而是因为「两处」意味着「以后要改两处」。
</Callout>

---

顺带提醒一个实现细节：主题必须在首帧之前定下来，否则会先闪一下浅色再切成深色。把读 `localStorage` 的那段脚本内联在页面头部同步执行，别放到组件里——放组件里就晚了。

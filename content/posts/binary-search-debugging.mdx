大部分人调试是「扫读式」的：从头看代码，一边看一边猜哪里可能有问题。这种方式在问题简单时有效，一旦代码超过几百行，效率会断崖式下跌。

更好的做法是**二分定位**：每次用最少的操作，把「可疑范围」砍掉一半。

## CSS 被覆盖了

不用去看选择器优先级，直接删。

先注释掉一半的样式表，看问题还在不在。在，说明罪魁祸首在另一半；不在，说明就在这一半。重复几次，五六轮就能从两千行缩到一行。

比对着 DevTools 里那一长串划掉的选择器猜要快得多。

## 性能回归了

先在时间轴上找一个「明显还正常」的版本，再用 `git bisect` 在好的和坏的之间二分。

```bash
git bisect start
git bisect bad HEAD
git bisect good v1.4.0
# 之后每次 git bisect good / bad，大概 7 步就能定位到具体那个提交
```

一千个提交，七步。手工翻提交记录的话，可能一整天。

## 逻辑错了

在可疑函数的中间打一个日志，看输出对不对。

- 对 → 问题在后半段
- 错 → 问题在前半段

重复。对一个两百行的函数，五轮以内就能锁定到具体那一行。

<Callout type="note" title="为什么它这么有效">
因为「把范围砍一半」这个动作的代价是固定的，而收益是指数级的。你不需要聪明，只需要不厌其烦地重复它。
</Callout>

## 前提条件：你得能稳定复现

二分定位唯一的前提是「同一个操作，每次都能复现同样的问题」。如果问题是偶发的，先别急着二分——去找复现条件。

这时候要做的是反向确认：记录每次出现时的环境、数据、时序，找出共同点。这一步没有捷径，但一旦复现稳定了，后面的二分就是机械劳动。

---

这个方法听起来笨，笨到不像一个「技巧」。但我在真实项目里见到的差异是：同样一个问题，会用的人半小时解决，不会的人能查一整天。区别不在聪明程度，在于有没有在动手之前先想清楚「怎么把范围砍一半」。
